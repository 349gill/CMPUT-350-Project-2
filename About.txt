Overview: To run the game we create the engine, then load our resources (sounds, textures, etc.) into it using their respective resource managers. We also load our background and gameplay maps. We then create a player, attach components for gravity, movement, sprite, input and collision, and assign them to its ID.

Entity Manager:
   - The Entity Manager stores entities in a vector called mEntities, where each entity's ID is its index in that vector. Another vector, mInvalid, tracks whether each entity is valid. We mark removed entities as invalid instead of deleting them, so the indices of the other entities do not change.
   - When creating an entity, the manager assigns an ID based on the current size of mEntities. The entity is then added to the vector and marked as valid, and its component indices are initialized to kNullComponent, meaning that no components are attached yet.
   - Components are stored separately by type in ComponentStorage objects inside a tuple. The Entity Manager maintains an index table that connects each entity to its components, allowing systems to retrieve specific components.
   - AddComponent() attaches a component to an entity or updates an existing one. When a component is removed, its storage slot is marked invalid and added to a free list. This avoids unnecessary shifting of elements.

Resource Managers:
- The Sound Manager registers sounds using their file paths and assigns them names so they can be accessed across the game. It stores audio data in mSoundBuffers and playable sound instances in mSoundInstances, and allows multiple sounds to use the same loaded audio data. Systems retrieve sounds using GetSound(soundName) and can play them without loading the files again.
- The Sprite Manager loads textures and stores them in an unordered_map to avoid loading the same image repeatedly. When RegisterTexture() is called, it creates a sprite from the specified texture and stores it in a vector. Each sprite receives a SpriteID, which systems use with GetSprite() to retrieve the sprite for rendering.
- The Window Manager creates and manages the SFML rendering window using a shared_ptr. It stores the camera's world position and scale, allowing the game to convert between world coordinates and screen coordinates. It also provides functions for changing the camera position, adjusting zoom, and drawing debugging rectangles.

System Manager and Game Systems:
- The System Manager stores the game's systems in a vector of unique_ptr, which manages their memory automatically. AddSystem() registers systems, and Run() executes them sequentially in the order they were added.
- CollisionLateSystem stores each entity's previous collision box before it moves. InputSystem reads keyboard input and modifies the player's velocity to handle running, jumping, wall jumping, and dashing. GravitySystem applies acceleration to entities while accounting for collisions, falling speed, and temporarily disabled gravity. MovementSystem updates entity positions using their velocities, while CollisionSystem detects and resolves collisions with platforms, obstacles, and collectible stars.
- ScoreSystem updates the numeric sprites displaying the player's score. CameraSystem adjusts the camera's horizontal position to follow the player, while SpriteSystem renders entities using their sprite and location components. SpawnSystem creates collectible stars at specified intervals and assigns them components such as location, movement, sprite, and collision.
- The engine's Run() function repeatedly processes SFML events while the game window remains open. It clears the window and calls SystemManager::Run() to execute the registered systems. Finally, window->display() presents the completed frame before the loop repeats.

Game Components:
- LocationComponent stores an entity's position in the world, which all other positions and bounding boxes are relative to. MovementComponent stores the entity's velocity in the X and Y directions. GravityComponent stores acceleration and a timer that allows gravity to be temporarily disabled.
- CollisionComponent stores the current and previous collision rectangles, collision directions, and whether an entity is static or damaging. These flags allow systems to determine whether an entity is touching the ground, ceiling, or walls. RespawnComponent stores the location where an entity should return after dying.
- CameraComponent stores the camera's world position, scale, exclusion regions, and tracking speed. CameraFollower stores the EntityID of the entity being followed, allowing CameraSystem to retrieve its position. CameraShake stores the duration and offset intended for temporarily shaking the camera.
- InputComponent stores the entity ID, dash timer, and keyboard states using std::bitset. It maintains both the current and previous keyboard states to distinguish new key presses from held keys. InputSystem uses this information to control movement, jumping, and dashing.
- ScoreComponent stores the current score, sprite IDs for digits 0-9, and entity IDs for displaying the score. SpawnComponent stores the spawner's entity ID, spawn type, sprite ID, spawning intervals, and remaining spawning events. SpriteComponent stores a sprite ID, its drawing bounds, and whether it uses world-space or screen-space coordinates.

Game:
 - The platformer allows players to move, jump, wall jump, wall slide, and interact with obstacles using the movement and collision systems. Stars are generated by SpawnSystem and can be collected by the player to increase their score. The camera follows the player horizontally, and the player respawns at the start location after dying.
